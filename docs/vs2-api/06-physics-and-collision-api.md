# Physics, Shapes, Contacts, and Joints

## `PhysLevel` — the physics world

`org.valkyrienskies.core.api.world.PhysLevel` (`@VsBeta @PhysTickOnly`) is the
physics world for **one dimension**. Unlike the global `ServerShipWorld`, it is
dimension-specific. Verified signatures:

```java
String getDimension();
AerodynamicUtils getAerodynamicUtils();
PhysShip getShipById(long shipId);                       // null if absent
void physTick(double delta);
RayCastResult rayCast(Vector3dc start, Vector3dc direction,
                      double length, long... ignoredShips);
boolean enableCollisionBetween(long shipId0, long shipId1);
boolean disableCollisionBetween(long shipId0, long shipId1);
```

Notes:

* `enableCollisionBetween` / `disableCollisionBetween` return `boolean` (whether
  the change was applied), not `void`.
* `rayCast` requires a **normalised** direction per the API contract; the
  returned `RayCastResult` retains a `PhysShip` and must not be passed to the
  game thread.
* `physTick` is called by the physics thread; do not touch game-thread state
  from it.
* `getAerodynamicUtils()` exposes the atmospheric calculations for this level.

Internal `VsiPhysLevel` adds `getGravity()`, `getAllPhysShips()`, and joint
management: `getJointById`, `getJointsFromShip`, `getAllJoints`,
`getJointsByShipIds`, `addJoint`, `updateJoint`, `removeJoint`. See
[09-internal-apis-and-compatibility.md](09-internal-apis-and-compatibility.md).

## Contact points

`org.valkyrienskies.core.api.physics.ContactPoint` (`@VsBeta @PhysTickOnly`):

| Property | Type | Meaning |
| --- | --- | --- |
| `position` | `Vector3dc` | World-space contact point |
| `normal` | `Vector3dc` | Contact normal |
| `separation` | `Float` | Signed separation; negative means penetration |
| `velocity` | `Vector3dc` | Relative point velocity (A minus B) |

A contact point is a **physics sample**, not a Minecraft block coordinate or a
damage event. The narrow-phase manifold is generated by the active backend and
its exact contents are not guaranteed across backends. See
[04-events-and-callbacks.md](04-events-and-callbacks.md) for the enclosing
`CollisionEvent`.

## Ray casts

`RayCastResult` (`@PhysTickOnly`, a Kotlin `data class`) is:

| Property | Type | Meaning |
| --- | --- | --- |
| `hitBody` | `PhysShip` | The body that was hit |
| `distance` | `Double` | Hit distance |
| `hitNormal` | `Vector3dc` | Surface normal |
| `velocity` | `Vector3dc` | Surface linear velocity |
| `angularVelocity` | `Vector3dc` | Surface angular velocity |

Because it retains a `PhysShip`, copy the values you need before leaving the
physics thread.

## Body collision shapes

`org.valkyrienskies.core.api.bodies.shape.BodyShape` exposes `aabb: AABBdc`
(model space). The public primitive shapes:

| Shape | Parameters | Geometry |
| --- | --- | --- |
| `Box` | `halfLengths: Vector3dc` | Centred at origin; side length is `2 × halfLength` |
| `Capsule` | `radius`, `halfLength` | Centred at origin, aligned to the X axis |
| `Sphere` | `radius` | Centred at origin |
| `Wheel` | `radius`, `halfThickness` | Centred at origin in the YZ plane |
| `Voxel` | `definedArea: AABBic` + updates | Block-grid collision shape |

`Voxel` is the ship collision shape: `definedArea` declares the region in which
the voxel shape is defined; chunks outside it are treated as air by default.

```java
void applyUpdateAsync(VoxelUpdate update);   // may be called from any thread
void applyUpdateSync(VoxelUpdate update);    // physics thread only
```

Prefer `applyUpdateAsync`. `applyUpdateSync` may only be called from the physics
thread and dense synchronous updates can stall the tick.

`VoxelUpdate` identifies a chunk (`chunkX`, `chunkY`, `chunkZ`) and is built
through `VoxelUpdate.Builder.addBlock(x, y, z, block: VoxelType)`. `VoxelType`
is an opaque marker interface; the concrete types are internal (see below).

## Block-state collision shapes

Source: `org/valkyrienskies/core/api/physics/blockstates/*.kt`. These describe
Minecraft block collision geometry and material state. They are **not** a
mechanism for mutating blocks.

| Type | Meaning |
| --- | --- |
| `BlockShape` | Base shape; `boundingBox: AABBic` (integer 0–15) |
| `SolidBlockShape` | Base for solid shapes (`@NonExtendable`) |
| `BoxesBlockShape : SolidBlockShape` | Positive boxes, negative boxes, and collision points |
| `LiquidBlockShape` | Base for liquid shapes |
| `BoxBlockShape : LiquidBlockShape` | A liquid shape defined by its bounding box |
| `SolidState` | `elasticity` [0,1], `friction` [0,1], `hardness`, `shape` |
| `LiquidState` | `density`, `dragCoefficient` [0,1], `velocity`, `shape` |
| `CollisionPoint` | `x`, `y`, `z`, `radius` (double; float constructor available) |

`SolidState.Builder` and `LiquidState.Builder` are obtained from
`VsiCore.newSolidStateBuilder()` / `newLiquidStateBuilder()` or from a
`RegisterBlockStateEvent` (see
[08-minecraft-integration.md](08-minecraft-integration.md)). `BoxesBlockShape`
box coordinates must be in `[0, 15]`.

`SolidState` and `LiquidState` are registered against Minecraft `BlockState`s
via `RegisterBlockStateEvent`, including the waterlogged case where one block
has both a solid and a liquid state.

## Joints (internal)

Joints are **internal** API (`org.valkyrienskies.core.internal.joints`) and are
`@PhysTickOnly`. They are managed through `VsiPhysLevel`, not the public
`PhysLevel`. The base is `VSJoint`:

```kotlin
interface VSJoint {
    val shipId0: ShipId?              // null = attached to the world
    val pose0: VSJointPose
    val shipId1: ShipId?              // prefer non-null; Core stores the null one as id0
    val pose1: VSJointPose
    val maxForceTorque: VSJointMaxForceTorque?
    val jointType: VSJointType
    val compliance: Double            // inverse spring stiffness; default 1e-10
    var shouldBeSerialized: Boolean
    fun serialized(): VSJoint
    fun offsetLocalPositions(offset0: Vector3dc, offset1: Vector3dc): VSJoint
    fun scaleLocalPositions(scale0: Double, scale1: Double): VSJoint
}
```

`VSJointType` = `FIXED, DISTANCE, PRISMATIC, SPHERICAL, REVOLUTE, GEAR,
RACK_AND_PINION, D6`. `VSJointId` is an `Int`.

| Joint | Summary |
| --- | --- |
| `VSFixedJoint` | Rigid attachment, no degrees of freedom. Stronger than collision forces; use sparingly. |
| `VSDistanceJoint` | Controls distance between two points; rope/cable/spring (`minDistance`, `maxDistance`, `tolerance`, `stiffness`, `damping`). |
| `VSRevoluteJoint` | Hinge/door; single rotation axis, angular limits, optional drive (`driveVelocity`, `driveForceLimit`, `driveGearRatio`, `driveFreeSpin`). |
| `VSPrismaticJoint` | Linear motion along an axis, with a linear limit pair. |
| `VSSphericalJoint` | Ball-and-socket; rotation about a point with an optional limit cone. |
| `VSGearJoint` | Gear ratio between two hinges. `@UnavailableInKrunch`. |
| `VSRackAndPinionJoint` | Rack-and-pinion mechanism (`hinges`, `ratio`, tooth/rack data). `@UnavailableInKrunch`. |
| `VSD6Joint` | Fully configurable 6-DOF joint (motions, linear/angular limits, drives). `@UnavailableInKrunch`. |

`@UnavailableInKrunch` means the joint does not function when the physics
backend is the original Krunch; it requires the PhysX backend. The annotation is
a `@RequiresOptIn(Level.WARNING)`.

`VSJointPose(pos: Vector3dc, rot: Quaterniondc)`; `VSJointMaxForceTorque(maxForce:
Float, maxTorque: Float)`; articulation joints never break.

## Backend differences

Core exposes a common abstraction, but support differs by backend. The server
physics config selects the backend (`ConfigPhysicsBackendType`; the values are
`KRUNCH_CLASSIC` (the default), `KRUNCH_PHYSX`, and `KRUNCH_JOLT`).

Known differences to account for:

* **Joints**: `GEAR`, `RACK_AND_PINION`, and `D6` are unavailable in Krunch
  Classic. `compliance` is used by Krunch Classic and ignored by Krunch PhysX.
* **Collision output**: emission cadence and contact-manifold contents are not
  specified as identical across backends. Tolerate repeated persistent events
  and empty contact collections.
* **Solver tuning**: `physicsSubSteps`, `krunchIterations`,
  `positionIterations`, `velocityIterations`, `maxDePenetrationSpeed`, and
  `physicsThreads` affect stability and performance.
* **`PhysTickEvent.delta`**: affected by `synchronizePhysics` and
  `physicsSpeed`.

Test against the backend you target; do not infer capability purely from the
interface hierarchy.
